## New problems introduced by the rewrite

**A. The `shouldRevalidate` rule, as stated, blocks Retry, Refresh and phase 2's post-sign-out bfcache guard - BLOCKING.** TECH §3 states the predicate as "when the pathname is unchanged and the only search-parameter difference is `expanded`, return `false`". On `router.revalidate()` the two URLs are *identical*, so the set of differing parameters is empty and the natural implementation (`differences.every(name => name === 'expanded')`) is vacuously true and returns `false`. That is not academic: `shouldRevalidateLoader` (router.js:2065-2071) lets the route's predicate override `defaultShouldRevalidate` even when `isRevalidationRequired` is true (set by `interruptActiveLoads`, router.js:1091), so a `false` here silently no-ops every revalidation. Consequences: invariants 70-72 (Retry) and 79 (Refresh) become unimplementable through `useRevalidator`; and because TECH puts the predicate on the **`authenticated`** route, phase 2's `createBackForwardRestore` (`/Users/sergeykhomyuk/System/Areas/Dev/github/hierarchy-tree/src/app/routing/createBackForwardRestore.ts:18`, which calls `router.revalidate()` on a persisted `pageshow` specifically so the guard re-runs after sign-out) stops re-running `requireSession`, breaking phase 2's behavior that invariant 187 promises is untouched. TECH risk 2 gestures at "too broad and Retry stops working" but the spec never states the rule that avoids it. It must say: return `false` only when there **is** a non-empty difference and every differing parameter is `expanded`; identical URLs must revalidate.

**B. Invariant 161's route-viewed premise is false** - detailed under finding 23 above. It is the seam between finding 1's fix and finding 23's fix: suppressing revalidation also suppresses the router's loading transition, and therefore the tracker's interaction and its `app.route_viewed`.

**C. Invariant 194 is double-assigned** (M1 explicitly, M5 via "183-196") while TECH asserts exactly-one assignment - detailed under finding 26.

**D. M2 owns invariants it cannot verify at its own boundary.** M2 takes "Invariants 41-57, 160-170, 173-174" with the boundary "**with the page still rendering phase 1's placeholder**". But invariant 166 (a failed photo reported without its URL) depends on the `Avatar.onImageError` callback and the row component, both M3; invariant 167 ("No telemetry event ... from this page carries ... a person's name or a photo URL") ranges over M3's toggle events (115) and M4's `*` event (141); invariant 169 ("The e2e suite asserts these events against the buffer sink") likewise. Either move 166-167/169 to M3/M5 or state that M2 verifies only the subset its code emits - as written, M2's boundary cannot honestly be called green.

**E. The photo-failure dedupe is per-Avatar-instance, not per row.** TECH §6 specifies `onImageError` "fired once per failed source"; invariant 97 promises "reported exactly once per row to telemetry, however many times the row re-renders". Concrete attack: collapse and re-expand the parent branch five times - each cycle unmounts and remounts the row, resetting `Avatar`'s `imageFailed` state, so the same person's photo failure is reported five times. TECH's named test ("firing the image error twice and asserting one event for 97") exercises a single instance and would not catch it. Decide whether the dedupe key is the row instance or the person id for the life of the load.

**F. The Retry/Refresh callback has no stated route into the feature.** TECH §3 places the `useRevalidator` wrapper in `src/app/`, but TECH §3's dependency object is enumerated as `(http, observability, clock)` plus `userId`, and §4 gives `HierarchyPage` no retry prop - yet the page renders the Retry and Refresh buttons (invariants 70, 79). Name the prop, or an implementer will be tempted to call `useRevalidator()` inside the feature and lose the `beginInteraction()` wrapping that invariant 72 depends on.

**G. `*` with nothing left to open is undefined.** Invariant 141 says the keystroke is "one action: one history entry, one live-region announcement naming how many branches opened, and one telemetry event". Press `*` twice on the same row: the second press opens zero branches. Does it still push an identical URL (making Back a visually no-op step), still announce, still emit? Every other toggle necessarily changes the set, so this is the only no-op-capable action and the only place the question arises.

**H. Minor: PRODUCT's header claim is slightly overstated.** It says "nothing inside this file cites a number", but "Decisions taken while specifying" item 8 cites "(see deviation 6)". The citation is correct (deviation 6 is the kit widening), so this is cosmetic - but the header sentence is a promise a future renumber could falsify.

**I. Minor: invariant 91's test wording is self-contradictory.** "expanding a leafless branch elsewhere in the forest must leave an untouched row's render count unchanged" - a leafless node has no expand control at all (invariant 105). The assertion is clear enough, the noun is wrong.

**J. Minor: invariant 96 does not match the kit derivation it names.** It says initials are "the first character of the first name and the first character of the last name ... using the existing kit derivation", but `src/shared/ui/deriveInitials.ts:5-6` splits the whole display name on whitespace and takes the first character of the **first** and **last word**. For a two-word first name ("Mary Jane Watson") those differ. The email-only case (invariant 55) does behave as specified - one word yields one character.
