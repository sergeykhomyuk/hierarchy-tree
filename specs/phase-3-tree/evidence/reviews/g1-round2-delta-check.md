## Verdict: 2 of 9 correct, 7 with problems

**1. PROBLEM (BLOCKING).** The new rule itself is right on all three counts: (a) a toggle diffs only `expanded` → non-empty set, all members `expanded` → `false`, and the predicate is reached because `route.lazy` is cleared to `void 0` after first resolution (`router.js:2187`) so `forceShouldLoad` at `:1953` no longer short-cuts it; (b) `router.revalidate()` → `interruptActiveLoads()` sets `isRevalidationRequired = true` (`:1091`) and re-navigates to `state.location` (`:480`), so current and next URLs are identical, the difference set is empty, and the predicate returns `defaultShouldRevalidate = true` (`:1963`, consumed at `:2065-2071` exactly as the spec quotes); (c) with no predicate on `authenticated`, `createBackForwardRestore.ts:18`'s `revalidate()` still re-runs `requireSession`. **But the unnoticed problem is exactly the thing the spec chose deliberately.** Because the `authenticated` route keeps revalidating on a toggle, `dsMatches.some(m => m.shouldLoad)` is true, so the short-circuit at `router.js:693` is *not* taken; `shouldUpdateNavigationState` is true (`:655`, since `isUninterruptedRevalidation` is false for a normal toggle navigation) and `:708` pushes `navigation = loadingNavigation`. `createInteractionTracker.ts:66-73` then sees `isNavigating && !tracking` → `startInteraction()` (new correlation id), and on settle emits `analytics.track('app.route_viewed')` (`:60`) — **one route-viewed event and one minted correlation id per toggle**. That falsifies PRODUCT invariant 161 verbatim and TECH's e2e assertion "**no** additional route-viewed event". Worse, the stated justification for index-only scoping is wrong: the spec's own defensive rule *cannot* return `false` on a bfcache revalidate, because that revalidation has identical URLs and therefore an empty difference set. Applying the same predicate to the `authenticated` route is safe, restores the `:693` short-circuit (no `dataStrategy` is passed — `createApplicationRouter.ts:10` — and no route declares `middleware`), and makes 161 true. Secondary, unstated cost of the current choice: every toggle produces fresh `authenticated` loader data, re-rendering the whole authenticated shell.

**2. PROBLEM (non-blocking).** The channel matches LoginRoute's established pattern (`LoginRoute.tsx:11,28-35`) and `useRevalidator` exists in react-router 8.3.0, but three defects. (i) The wrapper order is wrong: `revalidate()` first calls `updateState({ revalidation: "loading" })` (`router.js:476`) while `navigation.state` is still `idle`, so the tracker's subscriber runs with `isNavigating === false && tracking === true` and executes `settle()` — emitting a **spurious `app.route_viewed` on every Retry/Refresh** and closing the interaction before the users request even starts (the later `endInteraction()` is then a no-op). The correlation id survives (`correlationId` is not cleared by `settle`), so invariant 72 holds, but the buffer contents do not match anything either document states. (ii) `dependencies` is listed as `(http, observability, clock)`, yet the page issues no request — `fetchPeople` is called by the app-layer loader (TECH §3), so `http` on the page is dead and invites exactly the render-then-fetch the spec forbids in invariant 58. (iii) TECH concedes "a `useRevalidator()` call inside the feature would compile, work, and quietly lose the new correlation id", which means invariant 193's "unbypassable" has no test and no lint rule; `no-restricted-imports` for `src/features/*/**` (`eslint.config.js:578-591`) bans only sinks, not `useRevalidator`.

**4. PROBLEM (BLOCKING).** The new premise is false. "A toggle runs no loader" is untrue while the `authenticated` route revalidates (see item 1); therefore the short-circuit at `router.js:693` is not taken, the navigation *does* enter its loading state (`:705-713`), the tracker *does* open an interaction (`createInteractionTracker.ts:67-69`) and *does* emit route-viewed (`:60`). Every clause of 161 after "not one per toggle" is currently wrong.

**5. PROBLEM (non-blocking).** The design is coherent as far as it goes: `Avatar.tsx:27,39` owns `useState`/`onError` internally so an added `onImageError` fires once per mounted failed source, `flattenVisible` genuinely unmounts collapsed rows, and TECH's three-times-collapse remount test is the right discriminator. What is missing is the other half of "per person **per load**": neither document says where the dedupe set lives nor that it must **reset when a new payload resolves**. Since `HierarchyPage` does not remount across a Retry revalidation, a naive ref would suppress the second load's report forever, and no named test covers "retry, same photo fails again, one further event".

**6. PROBLEM (BLOCKING).** The seam is real — `httpRequest.ts:8` is `signal?: AbortSignal` and `createHttpClient.ts:84-86` merges it with the deadline controller via `AbortSignal.any` — but the causal claim is false for this loader shape. The loader returns `{ hierarchy: Promise<…> }` synchronously, so `handleLoaders` resolves in a microtask, `completeNavigation` runs, and `router.js:559` sets `pendingNavigationController = null` **without aborting**. A later navigation's `pendingNavigationController && abort()` (`:490`) therefore finds nothing. Consequences: `cancelled` is effectively unreachable through a superseded navigation, so M2's boundary item "an aborted navigation" cannot be produced in Playwright at all; and the abandoned request of a double-click runs to completion and emits its own event, which the "expected buffer contents exactly" assertion will see.
