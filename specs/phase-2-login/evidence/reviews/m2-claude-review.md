I traced the focus-handling, busy-button, and no-match-single-alert designs described as known context and found them implemented as claimed.

I also hand-traced two behaviors not covered by the "known context" list: the interaction-tracker's new `beginInteraction()` against its existing router-driven `tracking` state machine, and the Retry control's reachability with empty form fields.

**Verdict: 4 findings (0 blocking)**

1. **`beginInteraction()` leaves the shared interaction tracker permanently "tracking" after a login submission that does not navigate, so the *next* real navigation reuses the abandoned attempt's stale correlation id instead of minting a fresh one.**
   `src/app/routing/createInteractionTracker.ts:39-44,56-68` (new `beginInteraction`/`startInteraction` wiring), consumed at `src/app/routing/routes/LoginRoute.tsx:32` -> `src/features/auth/useLoginSubmission.ts:54`.
   `beginInteraction()` is literally `startInteraction()`: it sets `tracking = true` and mints a new id, exactly like the router-driven path does on navigation start. But it has no paired "end" call for the case where the submission does *not* lead to `dependencies.navigate(...)` - i.e. every `noMatch` and `serviceProblem` outcome. Trace: user is on `/login` (settled, `tracking=false`), submits, gets `noMatch` -> `tracking=true`, `correlationId=id1`, no navigate call. If the user now does *any* real SPA navigation that doesn't go through `beginInteraction()` again (e.g. browser Back/Forward, which react-router's data router does intercept and drive through `state.navigation.state`), `attach()`'s listener sees `isNavigating && !tracking` = `true && false` = `false` on the `LOADING` transition, so it skips `startInteraction()` and the stale `id1` is reused for that unrelated navigation. `currentCorrelationId()` is the single source used app-wide for `createHttpClient`'s wire trace id (`createRuntime.ts:66`) and for uncaught-error reporting (`reportRootError.ts:20`), not just auth, so any http call or error surfaced during that one subsequent navigation is misattributed to the abandoned login attempt's id. `createInteractionTracker.test.ts` was not extended to cover `beginInteraction`'s interaction with the router lifecycle, so nothing catches this. No loader/http call happens on navigation in M2 itself (routes have no loaders yet per `routeDefinitions.ts`'s own comment), so the immediate blast radius today is confined to error-boundary correlation-id attribution; it will bite once M3/M4 add loaders.
   Non-blocking (no functional break in M2; a trace/log-correctness gap in a stated design invariant).

2. **The Retry control has no explicit readiness guard and relies entirely on the browser's native `required`-attribute validation to stop `deriveSecret` from throwing on an empty field; this is untested and asymmetric with the main Login button.**
   `src/features/auth/LoginAlert.tsx:34` (`<Button variant="secondary" type="submit" onClick={props.onRetry}>` - no `disabled`) vs `src/features/auth/LoginPage.tsx:131-137` (main button: `disabled={!isReady}`); the unguarded path reaches `src/features/auth/useLoginSubmission.ts` -> `deriveSecret`'s `throw new RangeError(...)` on an empty trimmed email or empty password.
   Reachable sequence: reach `serviceProblem` (a transient 5xx/network failure), then clear the password field (fields are not `readOnly` in this state) and press Retry or Enter. In a real browser this is currently blocked by the native constraint validation triggered by `required={true}` on both `Input`s (set unconditionally via `FieldContext` in every non-`noMatch` case) - the browser withholds the `submit` event entirely, so React's `action` never runs. That protection is implicit, not asserted by any test (`LoginPage.test.tsx`'s retry test only exercises a *non-empty* replacement password), and it is the only thing standing between this UI and an uncaught `RangeError` bubbling out of the `useActionState` action into `RouteErrorBoundary` (crashing the whole app shell, not just the card). If `required` were ever dropped from one field, or this ran through a path that bypasses interactive validation, the crash would be live with no defensive code in `useLoginSubmission` to catch it.
   Non-blocking today (native validation covers it in-browser), but worth an explicit guard or test given the asymmetry with the main button's own `disabled={!isReady}`.

3. **`LoginAlert.tsx`'s comment claims both fields get `aria-describedby` pointing at it in the service-problem state, but `LoginPage.tsx` only wires that for the no-match state.**
   `src/features/auth/LoginAlert.tsx:16-20` ("no field-level message is ever rendered, so both fields point their aria-describedby at this one element instead" - stated for "both the no-match and service-problem states") vs `src/features/auth/LoginPage.tsx:76-78` (`fieldContextValue` sets `describedBy: ALERT_ID` only when `noMatch` is true; the `serviceProblem` branch gets `{ invalid: false, required: true }` with no `describedBy`).
   The actual behavior (not linking describedby for a non-field-validation service error) is arguably the more correct ARIA choice, and no test asserts the comment's stronger claim either way, so this reads as a documentation/comment accuracy slip rather than a functional bug - but it's exactly the kind of comment-vs-code mismatch invariant-tracing is meant to catch.
   Non-blocking.

4. **`auth.signed_out` is added to the analytics catalogue but is not fired or consumed anywhere in this milestone.**
   `src/platform/observability/analyticsEvents.ts:10`, exercised only by its own catalogue-shape unit test (`analyticsEvents.test.ts`), with zero call sites in `src/`.
   Same pattern as the M1-flagged `redact()` scope creep: safe in isolation, but it's a piece of surface area shipped ahead of the milestone (sign-out) that actually needs it, undocumented as a deliberate gap-fill the way `resolveDestination`'s barrel export is.
   Non-blocking.

## Answers to review questions

- **Correctness (bugs, edge cases, boundaries)**: No user-reachable crash found (finding 2's path is currently blocked by native HTML5 validation). The five-state derivation in `loginCardState.ts` is a straightforward, fully-covered pure function (idle/ready/submitting/noMatch/serviceProblem, with the `isPending`-wins-over-settled-result rule explicitly tested). The genuine correctness issue is finding 1, an interaction-tracker state-machine gap introduced by this diff's `beginInteraction` addition, not present in M1.
- **Contract**: The five-state rendering, the single card-level alert with no per-field message (invariants 51/52/109), the always-present `FieldContext.Provider` (focus-preservation fix), and the busy-button's focusable-but-blocked-click design all match their invariant comments when checked against the code. One exception: finding 3, where `LoginAlert.tsx`'s comment overstates the describedby wiring for the service-problem state relative to what `LoginPage.tsx` actually does.
- **Regressions**: `AuthPlaceholderPage`'s deletion is clean - grepped the full `src/` and `e2e/` trees for any remaining reference to it or to the old `login.title`/`login.message` catalogue keys and found none; all six touched e2e specs and `features.test.tsx` were updated consistently. `Button`/`Input`'s kit changes are strictly additive (new optional props, new busy/readOnly branches) with no change to existing call sites' output. The one cross-cutting behavior change this milestone introduces is finding 1 (interaction-tracker state leakage), which is new in this diff, not a carry-over from M1.
- **Test honesty**: The unit tests for `loginCardState`, `useLoginSubmission`, and `LoginPage` are concrete and exercise real state transitions (dedup-on-double-submit at the actual `useActionState` level, abort-on-unmount with a real `AbortController`, retry re-deriving from live field values with a request-path diff assertion) rather than echoing the implementation. Two gaps found: (a) `createInteractionTracker.test.ts` was not extended to cover `beginInteraction`'s interaction with the router lifecycle (finding 1), and (b) no test exercises Retry with an emptied field (finding 2). N>1 doesn't apply in the list sense here (login is a single-entity flow); the closest analogue - two submit buttons coexisting in the DOM during `serviceProblem` - is not separately tested (no assertion that the correct button wins the accessible-name lookup, though this is low risk since the labels differ).
- **API-mocking soundness (route-matching order)**: Verified. Playwright resolves a URL against routes in the reverse of their registration order (LIFO), so `apiMocks.ts`'s two specific routes, registered *after* `routeMocks.ts`'s catch-all abort-everything-off-origin block, correctly win for `https://gongfetest.firebaseio.com/secrets/*.json` and `/users/*.json`. Confirmed `gongfetest.firebaseio.com` is genuinely `configurationSchema.ts`'s `VITE_API_BASE_URL` default and no `.env` override exists, so the e2e preview build actually talks to that origin. `deriveSecret`'s uppercase-hex output and `secretResourcePath`'s `/secrets/${secret}.json` shape line up with `apiMocks.ts`'s `pathSegment()` parsing with no case or encoding mismatch.
- **"Hang forever" mock leak risk**: Not a cross-test leak. The never-resolving `Promise<never>` is registered via `page.route()` on that one test's own `page` fixture; Playwright's default test isolation gives each `test()` a fresh context/page, so the dangling handler and its unresolved promise are confined to that test's lifecycle and are discarded (GC'd) when the page is torn down, not shared with subsequent tests. Within the same test, the follow-up `page.goto('/login')` calls correctly discard the still-pending request via browser navigation rather than waiting on it, as the test's own comment states.
