# Coding

These principles govern every implementation task, regardless of scope.

## Think before coding

Before writing anything, surface what you know and don't know:

- State your assumptions explicitly. If you're making a choice the user hasn't specified, say so.
- If multiple valid interpretations exist, name them and ask — don't silently pick one.
- If a simpler approach exists, say so. Disagreeing with the stated approach is appropriate when you have good reason.
- If something is genuinely unclear, stop and ask. Naming the confusion is more useful than guessing through it.

The goal is to avoid discovering a misunderstanding after writing 100 lines.

## Simplicity first

Write the minimum code that solves the stated problem:

- No features beyond what was asked.
- No abstractions unless the code is called from multiple places.
- No "flexibility" or "extensibility" that wasn't requested.
- No error handling for scenarios that can't happen given the surrounding code.
- If you write 200 lines and it could be 50, rewrite it before sharing.

The test: "Would a senior engineer reading this say it's overcomplicated?" If yes, simplify.

## Surgical changes

When editing existing code, touch only what the task requires:

- Don't clean up adjacent code, comments, or formatting that isn't broken.
- Don't refactor things while you're in there.
- Match the existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it in a comment to the user — don't delete it.

When your changes leave orphans, clean them up:

- Remove imports, variables, and functions made unused by YOUR changes.
- Don't touch pre-existing dead code unless explicitly asked.

The test: every changed line should trace directly to the user's request.

## Goal-driven execution

Before starting a multi-step task, transform the vague goal into something verifiable:

- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For tasks with more than one step, state a brief plan before starting:

```
1. [step] → verify: [check]
2. [step] → verify: [check]
3. [step] → verify: [check]
```

Strong success criteria let you loop independently. Weak ones ("make it work") require constant back-and-forth with the user.

# TypeScript Coding Conventions

## Type safety

Declare explicit types for function parameters, return values, and data structures. For input of truly unknown shape, use `unknown` and narrow with a type guard before use.

Never use `any`, `as any`, `as SomeType` (to silence a mismatch), or `@ts-ignore`. Fix the underlying type instead.

```ts
// BAD
function processData(data: any) {
  return data.value;
}

// GOOD - declared shape
function processData(data: { value: string }) {
  return data.value;
}

// GOOD - unknown input narrowed by a type guard
function hasValue(data: unknown): data is { value: string } {
  return typeof data === 'object' && data !== null && 'value' in data;
}

function processData(data: unknown) {
  if (!hasValue(data)) throw new Error('Invalid data');
  return data.value;
}
```

## Existence checks

Prefer `!!value` over `value !== null` or `value !== undefined` when the goal is to check that something exists and is usable - not to distinguish between `null` and `undefined`. The double-negation coerces to boolean and guards against both absent states at once, which is usually what you want.

```ts
// BAD - verbose and only guards one absent state
if (user !== null) { ... }

// BAD - still only guards one absent state
if (user !== undefined) { ... }

// BAD - verbose pair when you don't care which absent state it is
if (user !== null && user !== undefined) { ... }

// GOOD - short, guards both null and undefined
if (!!user) { ... }
```

Reserve explicit `=== null` or `=== undefined` checks for the rare cases where the distinction actually matters (e.g., an API that treats `null` and `undefined` differently, or when you need to explicitly handle one but pass through the other).

## Naming

Use full descriptive identifiers: `response`, `declaration`, `category`, `error`. Don't shorten to `r`, `decl`, `cat`, `e`. Code is read more often than it is written.

## Module organization

### One public symbol per file

Each file exports exactly one public symbol (utility, hook, type, or component). The filename matches the symbol:

- Utility / helper: `lowerCamelCase.ts` (`formatDate.ts`, `uniqueBy.ts`)
- Hook: `useFoo.ts`
- Type-only module: `lowerCamelCase.ts` matching the type name

Helpers used only by that symbol stay in the same file. Helpers reused elsewhere move to their own file.

### Barrel exports

Every multi-file folder has an `index.ts` that re-exports its public surface. Consumers import from the folder, never from internal paths.

- `index.ts` contains re-exports only - no side effects, no top-level code
- Put initialization in a named function in a separate file (e.g. `initFoo.ts`) and call it explicitly from the entry point

### Low coupling

Shared abstractions stay generic. A utility or component in a shared directory must not import feature-specific types. If two shared modules need a common type, extract it to a lower-level shared file rather than coupling them to each other.

## Enums and constants

### Categorical values - use a const object

Use `as const` objects instead of `enum`. They compile to plain objects, avoid TypeScript enum pitfalls, and work naturally as types.

```ts
// BAD - literal union scatters values, no single source of truth
type Status = 'pending' | 'active' | 'completed';

// BAD - TypeScript enum (runtime overhead, reverse mapping surprises)
enum Status {
  Pending = 'pending',
  Active = 'active',
  Completed = 'completed',
}

// GOOD
const Status = {
  Pending: 'pending',
  Active: 'active',
  Completed: 'completed',
} as const;

type Status = typeof Status[keyof typeof Status];

function setStatus(status: Status) { ... }
setStatus(Status.Pending);
```

### Magic values - extract to named constants

Lift hardcoded labels, keys, thresholds, and timeouts into named constants. Use `as const` objects for grouped config:

```ts
const TIMEOUTS = {
  DEFAULT_DELAY: 5000,
  RETRY_DELAY: 3000,
} as const;
```

Co-locate constants with the code that owns them; lift shared constants to a common directory. Each constant module follows the one-symbol-per-file rule.

# React Coding Conventions

File and module organization (one symbol per file, barrel exports, hook and utility filenames, type-only modules) live in the typescript-coding skill. This skill covers React-specific conventions only.

## Memoization

Re-renders compound quickly. Don't skip memoization assuming any single re-render is cheap.

### Components

Wrap every exported component in `memo`, with a named inner function so it shows up clearly in React DevTools and stack traces:

```tsx
export const MyComponent = memo(function MyComponent({ prop1, prop2 }: MyComponentProps) {
  return <div>...</div>;
});
```

### Hooks

- `useMemo` for derived or expensive values: filtered arrays, grouped maps, sorted lists, anything computed from props or context in render
- `useCallback` for callbacks passed to children
- Dependency arrays must include every value the body reads. A stale closure is a silent bug
- An intentionally empty dependency array gets a one-line comment explaining why

### Inline callbacks in lists

Don't pass inline JSX callbacks (`onClick={() => onSelect(item.id)}`) to list items or reusable controls. They allocate a new function on every render and defeat the child's `memo`. Use a stable memoized handler and pass data through a DOM attribute or item prop:

```tsx
// BAD - new function each render, closes over item.id
<Item onClick={() => onSelect(item.id)} />

// GOOD - stable reference, id flows through dataset
const handleSelect = useCallback((event: React.MouseEvent<HTMLLIElement>) => {
  onSelect(event.currentTarget.dataset.id!);
}, [onSelect]);

<Item data-id={item.id} onClick={handleSelect} />
```

## Logic isolation

Components render. Hooks and utilities compute. Extract business logic into custom hooks, context providers, and utility functions. Keep generic helpers in a shared location; co-locate domain-specific logic with the feature that owns it. Only route-level or page components own data fetching or state orchestration directly.

Don't inline data transforms, filtering, or derived-state computations in a component body. They become untestable and unreusable.

## Components

### File naming

Component files use `PascalCase.tsx` matching the exported symbol (`SystemCard.tsx`).

### Exports

Use named exports for components and hooks, including route files. No default exports.

### Props

Destructure props at the function signature. Declare a co-located `FooProps` directly above the component, not in a separate types file:

```tsx
type FooProps = {
  label: string;
  count: number;
};

export const Foo = memo(function Foo({ label, count }: FooProps) {
  ...
});
```

- Children only: `type FooProps = React.PropsWithChildren`
- Children plus other props: `interface FooProps extends React.PropsWithChildren { otherProp: string }`
- Never declare `children?: ReactNode` manually
- Don't pass props through intermediate components that don't use them. Lift to context or a custom hook instead

## Accessibility

Use the right semantic element for the job: `button`, `nav`, `main`, `section`, `article`. Add `aria-label` to icon-only or otherwise unlabeled interactive controls. Don't use a styled `div` or `span` where a semantic element exists.

# Evidence-Backed Review

## When to use

Use this skill when:
1. The user asks for a skeptical review of a diagnosis, bug report, or verification document.
2. The user scopes review to a specific diff, branch, spec, or nested repo.
3. The review must stay read-only and every code claim needs file:line backing.

Do not use this skill when:
1. The user wants implementation changes instead of a review.
2. The request is broad architecture advice with no concrete repo evidence to inspect.

## Inputs / context to gather

1. Confirm the exact review target from the user wording: diagnosis doc, named diff, branch, or spec folder.
2. Identify the real working repo. In nested workspaces, verify whether the changed code lives in a sub-repo such as `debug/run-06/app`.
3. Find the supporting evidence files first: specs folders, recorded unit/e2e outputs, verification docs, and relevant source files.
4. Check for explicit constraints such as "Do not modify any files", "fresh thread", or "do not reference prior thread".
5. If the user supplied an exact shell or `git diff` command, record it as required evidence and execute it before forming the verdict.
6. If the user names accepted risks, record their exact boundary so new findings are not confused with risks they explicitly excluded from blocking status.

## Procedure

1. Restate the review scope in one sentence and treat it as a hard boundary.
2. Validate the target path before trusting the prompt. If the named file is missing, search the scoped repo for the actual artifact and note the mismatch.
3. Read the target artifact, then inspect the exact source files it depends on.
4. Execute any user-required command before analyzing or summarizing the diff.
5. For every code-related conclusion, record the exact `path:line` evidence that supports it.
6. Inspect tests and recorded evidence logs before judging coverage or correctness.
7. If the request is a diff review, verify the actual changed repo and branch before reading the patch.
7. Separate:
   1. verified code facts,
   2. claims that are unsupported or overstated,
   3. missing considerations such as broader collision surfaces or missing regressions.
8. Write the review in the user-requested structure. If none was specified, default to:
   1. Verdict
   2. Verified claims
   3. Disputed or unverified claims
   4. Missed considerations
   5. Recommendation

## Efficiency plan

    12	## Skills
    13	
    14	Invoke these for any implementation work, together, before writing code:
    15	
    16	- `/coding` - baseline discipline for every change: understand first, keep the diff minimal, define what "done and verified" means.
    17	- `/typescript-coding` - type safety, naming, module organization, constants. Any `.ts` work.

    19	
    20	## Core principles
    21	
    22	- **The brief bounds the features, not the engineering.** Depth goes into how the requested behavior is built - never into unrequested features.
    23	- **Boundaries are enforced, not suggested.** `app` composes, `features/*` own a slice end to end behind a single entry, `shared` is domain-free, `platform` adapts the outside world. No cross-feature imports, no deep imports. Lint failures on this are design feedback, not obstacles.
    24	- **Domain logic stays pure.** Tree building and flattening are framework-free, synchronous, and fully tested. Nothing in the domain layer imports React.
    25	- **Validate at the boundary, tolerate bad rows.** External JSON is parsed with Zod before it becomes a domain type; a malformed row is dropped and reported, never allowed to crash a page.
    26	- **Every data surface has four states.** Skeleton, error with recovery, empty, data. A component that only handles the happy path is unfinished.
    27	- **Accessibility is part of the definition of done.** The tree implements the full ARIA tree keyboard contract. Assert it in tests rather than claiming it in prose.
    28	- **No user-visible string in code.** Strings live in i18next catalogues; dates, numbers and lists format through `Intl`.
    29	- **Instrument what you build.** Requests, errors and meaningful interactions go through the observability facade with a correlation id. Never log or transmit secrets, passwords or tokens.
    30	- **Prefer platform and React primitives over dependencies.** A new runtime dependency needs a reason that survives the bundle budget.
    31	- **Tests are the evidence.** Pure domain near 100%, components by behavior and keyboard, e2e against Playwright route mocks including failure paths. Do not report work as done on an unrun suite.
