# G1 adversarial grill - phase-1-setup

Reviewer: `agentic-loop:loop-spec-validator` in grill mode, fresh context, read-only by tool restriction (Read/Grep/Glob only).
Date: 2026-08-13. Brief: break PRODUCT.md + TECH.md - contradictions, untestable invariants, infeasible claims checked against real versions, missing edge cases, the milestone split, scope drift against ROADMAP.md phase 1, the three decisions taken during specification, and the specs' own "placeholder app may be too empty" risk.

## Verdict

**26 findings (10 blocking)**

---

1. **The cache's TTL is a per-call argument, so two callers of the same key can disagree about freshness — which is exactly what invariant 37 forbids, and the named check cannot detect it.** | PRODUCT 37 ("Freshness is defined in exactly one place. A loader and a component reading the same key see the same freshness decision") vs TECH 3.3 `read<Value>(key: CacheKey, load: () => Promise<Value>, { timeToLiveMilliseconds }): Promise<Value>` | A phase-3 loader passing 30 s and a component passing 5 s for `/users.json` produce different freshness decisions from the same entry. TECH's check for 37 ("the freshness function is exported and both read paths are asserted to call it") passes against precisely that broken implementation, because both paths *do* call `isFresh` — with different arguments. The TTL must be bound to the key (registered per resource) or invariant 37 is unenforced. | **BLOCKING**

2. **Invariants 38 and 40 give contradictory answers for a read that arrives during a revalidation, and TECH's "guarded by the same in-flight slot" does not choose.** | PRODUCT 38 ("N concurrent reads of the same key **while a request is outstanding** produce exactly one transport call, and **all N resolve with the same value**") vs PRODUCT 40 ("a read after the TTL **returns the stale value immediately**") | Concrete sequence: entry stored at t=0, TTL 1000; read A at t=1500 returns stale and starts revalidation; read B at t=1600 arrives while that request is outstanding. Per 38 B must resolve with the same value as the other in-flight reader (the fresh one, after waiting); per 40 B must get the stale value now. Both are stated as invariants, both have unit checks in TECH ("38 - unit: N concurrent reads, one transport call, identical resolved values"; "39, 40 - unit: ... asserting call counts"), and the implementer will make one of the two tests unwritable. | **BLOCKING**

3. **Nothing can legally hand the ring buffer's `read()` to `create-runtime.ts`: the facade is asserted to expose exactly three keys and sink modules are lint-banned outside the facade.** | TECH 3.4 ("When `configuration.telemetryBufferHandle` is true, `create-runtime.ts` attaches a frozen `{ read }` object at `globalThis.__hierarchyTreeTelemetry`") vs PRODUCT 45 / TECH validation 45 ("unit (the facade's exported surface is exactly three keys)") and TECH 2.3's `no-restricted-imports` group `['@platform/observability/sinks/*', '**/observability/sinks/*']` | All three available routes break something as written: returning a fourth key fails the invariant-45 unit test; importing `ring-buffer-sink` from `app` fails lint; having `create-observability` attach the global itself contradicts "create-runtime.ts attaches" and puts a `globalThis` write inside `platform` with no invariant covering it. Invariant 49 ("The ring buffer is readable, so e2e asserts on what was recorded") and the whole `telemetry-buffer.spec.ts` depend on resolving this first. | **BLOCKING**

4. **`ErrorSurface` is specified to call `useNavigate()`, but `RootErrorBoundary` renders it from above `RouterProvider`, where that hook throws — turning the error path into the blank page invariant 91 forbids.** | TECH 5.4 ("Both render the same `ErrorSurface` component… The action calls `useNavigate()(0)`… and otherwise navigates to `/`") vs TECH 5.2's order `runtime --> i18n --> boundary --> router` | The "otherwise" branch is exactly the `RootErrorBoundary` case, and `useNavigate()` outside a `<Router>` throws "useNavigate() may be used only in the context of a <Router> component". An error caught by the root boundary would therefore throw again while rendering the recovery UI, producing an unstyled blank page — the precise failure invariants 91 and 93 exist to prevent, in the one code path that has no e2e coverage. | **BLOCKING**

5. **A caller-initiated abort has no representable outcome: the failure union has exactly four members and none of them means "cancelled".** | PRODUCT 25 ("A caller-initiated abort is never retried and is not reported as an application error") and PRODUCT 33 ("Failures are exactly one of four types… The union is exhaustive") vs TECH 3.2 ("if `callerSignal.aborted` after a failure, the client returns without retrying and emits no error-level record") | TECH never says what `HttpResult` a caller abort yields. The mapping rule ("every non-`Response` throw from the transport becomes `{ kind: 'network' }`") makes cancellation indistinguishable from a real network failure, so a phase-2/3 caller that cancels a request on unmount renders an error state for its own cancellation. Adding a fifth `{ kind: 'cancelled' }` violates invariant 33 as written; returning `network` violates 25's "not reported as an application error". The user has to pick one. | **BLOCKING**

6. **The specified `createFakeClock` cannot simultaneously satisfy the timeout tests and the retry-delay tests — an "instantly-resolving sleep" fires every request's deadline on the next microtask.** | TECH 6.1 ("`createFakeClock` (manual `now` advance and an instantly-resolving `sleep` that records the requested delay)") vs TECH 3.2 ("one `AbortController` per attempt, aborted by `clock` after `timeoutMilliseconds`") and PRODUCT 115 ("Unit and e2e runs are deterministic") | If the deadline is `clock.sleep(timeout).then(abort)` and `sleep` resolves immediately, every HTTP unit test races its fake transport against an already-fired deadline; whichever wins depends on microtask ordering inside the fake transport, so the whole `src/platform/http` suite is non-deterministic. The clock needs separately controllable timers (a manual timer queue) versus the pass-through used for backoff, and the spec must say which. | **BLOCKING**

7. **M1's verification claim is false as written: `npm run verify` includes `size` and `test:coverage`, and neither can pass in M1.** | Milestone split, M1 ("every npm script from 7.1 in place"; "Verifiable because: `npm run verify` runs end to end and passes") vs 7.1 (`verify` = "the seven gating scripts chained with `&&`") and M6 ("Delivers: `.size-limit.json` with real numbers") | In M1 there is no `.size-limit.json` and no route chunks, and TECH itself relies on "a glob matching no file makes size-limit fail" (7.3) — so `size` fails. Coverage thresholds of 85% are configured in M1 with a coverage `include` of `src/**/*.{ts,tsx}` and essentially no tests, so `test:coverage` fails (and `vitest run` with zero test files errors without `passWithNoTests`). The first milestone's entire boundary rests on a command that cannot go green; the same objection applies to M2, M3 and M4. | **BLOCKING**

8. **Invariant 86 (and the e2e half of 74) can never be proven in this phase: five of the eight kit components never render in a browser, and a component gallery is an explicit non-goal.** | PRODUCT 86 ("**Every kit component** renders correctly from a 320px viewport upward without horizontal overflow"), TECH validation 86 ("e2e: each route at a 320x640 viewport") vs TECH 5.5 ("a `Card` containing one `h1`, one paragraph of catalogue text… and nothing else") and PRODUCT non-goals ("A theme switcher, a design-system documentation site or a component gallery") | The only browser surfaces are two placeholder pages, the not-found page and the error surface — exercising `Card`, `Button`, `ErrorState` at most. `Input`, `Field`, `Avatar`, `Skeleton` and `EmptyState` have no rendered page anywhere, jsdom cannot decide overflow (TECH says so), and the phase forbids building the surface that would show them. Either 86 is scoped down to the components that actually render, or a non-goal is reopened. | **BLOCKING**

9. **Feature and kit tests cannot use the one real provider stack without failing the boundary rule the same phase installs.** | TECH 1 (`src/app/testing/render-route.tsx`) and PRODUCT 90 ("The provider stack is composed in exactly one place… Rendering a route in a test goes through the real stack") vs TECH 2.1 `'boundaries/include': ['src/**/*.{ts,tsx}']` and 2.2 `{ from: ['feature'], allow: ['shared','platform', same-feature] }` | Test files are inside the boundaries scope, so `src/features/auth/placeholder-page.test.tsx` importing `@app/testing/render-route` is a `boundaries/element-types` error. The three escapes each break something: duplicate the provider stack in the feature (violates 90), put it in `shared` (which may not import `app` or `features` either), or exempt `**/*.test.tsx` from boundaries (weakens invariants 1 and 12, and is nowhere stated). TECH only gestures at this in the fan-out paragraph ("`eslint.config.js` (rule overrides for test files)"). | **BLOCKING**

10. **"Interaction" is never defined, no module owns `startInteraction()`, and nothing in the plan emits `app.route_viewed` — yet the e2e asserts on both.** | PRODUCT 47 ("Every interaction has one correlation id"), TECH 3.4 (`'app.route_viewed': { routeId: string }`), TECH 6.2 ("asserts the expected records - a `app.route_viewed` per navigation") vs the file layout, which contains `correlation.ts` with `startInteraction / currentCorrelationId` and no caller; the only mention of a producer is a parenthetical in 5.4 ("set by a router subscription on every navigation") | The implementer must invent: does an interaction begin at navigation start or after the route resolves? Does the initial page load emit `route_viewed`? Does the aborted-chunk navigation emit one before it fails (the telemetry spec asserts both a `route_viewed` and exactly one `app.error_boundary_shown`)? Invariant 47's "the same id on the request record, the boundary report and the analytics event" also has no request record to correlate with in a phase where nothing fetches. | **BLOCKING**

11. **The claimed network stub does not exist for the suite that most needs it: the `platform` Vitest project has no `setupFiles`.** | TECH 6.1 (`platform` project: `environment: 'node'`, `include: ['src/platform/**/*.test.ts', …]` — no `setupFiles`; only the `ui` project lists `setupFiles: ['./vitest.setup.ts']`) vs TECH validation 32 ("the whole http suite runs with the fake transport **and the network stub in `vitest.setup.ts` active**, so a real call would fail the test") and PRODUCT 115 | The HTTP client tests live in `src/platform/http/*.test.ts`, i.e. in the project without the stub, so an accidental real `fetch` in the one module that is allowed to call `fetch` silently succeeds. The stated check for 32 is false about its own configuration. | non-blocking

12. **The live-smoke test file has no location in the layout and no exclusion from the default Vitest projects, so it can end up running on every pull request.** | TECH 1 (layout lists `vitest.live.config.ts` but no live spec file) and 7.4 ("It runs `npm run smoke:live`, which executes [an] `e2e`-free Vitest test against the real client and the real `fetch-transport`") vs 6.1's `platform` include `src/platform/**/*.test.ts` and PRODUCT 116 ("It never runs on a pull request or on `main`") | If the file lands as `src/platform/http/live-smoke.test.ts` it is collected by `npm run test:coverage` in CI and makes a live network call from a gating step — breaking 116 and 115 at once. 13. **The forced-error e2e flow collides with "every spec asserts the console collection is empty", and the two halves of TECH state different console contracts for that same spec.** | TECH 6.2 ("every spec asserts the collection is empty at the end. Its allow-list is empty, and stays empty") vs TECH validation 91 ("the console recorder asserts **no unhandled stack reached the page**") and 5.4 ("the e2e mocks the lazy route chunk request with `page.route(...)` to abort") | React 19's default `onCaughtError` logs every boundary-caught error via `console.error`, and React Router logs route errors as well; the aborted-chunk flow is designed to produce exactly such an error. On first run `error-boundary.spec.ts` fails its own console assertion, and the only fix the spec permits ("adding an entry requires the same argument as downgrading a lint rule") is the one it tries to forbid. 14. **A dynamically imported JSON catalogue becomes its own Rollup chunk, so the build-output check for lazy namespaces is vacuous and the per-route size budget does not measure the namespace.** | TECH 3.5 ("`const catalogue = await import('./locales/en/auth.json')` … so the JSON is bundled into that route's chunk by Rollup") and validation 62 ("a build-output assertion greps `dist/assets/login-route-*.js` for a hierarchy-only key and asserts it is absent") | Rollup makes every dynamic import a chunk boundary; with `chunkFileNames: 'assets/[name]-[hash].js'` the catalogue lands in `assets/auth-*.js`, not inside `login-route-*.js`. It also means `.size-limit.json`'s four globs do not cover the emitted catalogue chunks. | non-blocking

15. **"axe in both themes" cannot fail differently in jsdom: no stylesheet is applied and axe's colour-contrast rule does not run there.** | PRODUCT 87 ("assert zero axe violations, in both light and dark") and TECH 6.1 ("once with the default `matchMedia` stub and once with a stub reporting `prefers-color-scheme: dark`") | jsdom applies neither Tailwind's generated utilities nor `theme.css`'s `@media (prefers-color-scheme: dark)` block, and a `matchMedia` stub changes nothing about computed style, so the second run asserts the same DOM twice. ## Questions the specs do not answer

- **Is a request's deadline per attempt or per logical request?** TECH 3.2 puts one `AbortController` per attempt, so a caller passing `timeoutMilliseconds: 8000` can wait 16 s plus backoff. Invariant 23 says only "every request is given a deadline".
- **What happens to an in-flight read when `invalidate(key)` or `clear()` is called mid-flight?** Does the settling request still populate the entry (resurrecting invalidated data), and do the waiting readers receive it? Nothing in 42 or TECH 3.3 says.
- **Does the `traceparent` header trigger a CORS preflight against `gongfetest.firebaseio.com`?** The phase-1 live smoke runs under Vitest in Node, where CORS is not enforced, so a preflight rejection that would break phases 2 and 3 in the browser cannot be discovered by the probe invariant 116a defines.
- **What does a missing translation key render in a production build?** Invariant 63 covers development and tests only.
- **Which error, in which flow, exercises `RootErrorBoundary`?** It is specified (TECH 5.4, "catching everything else") but no unit or e2e flow drives it, which sits badly with both the 85% coverage threshold and invariant 136's ban on code with no caller.
- **Is `verify` allowed to be a subset of the gates in early milestones**, or does M1 need `size` and coverage stubbed? Related: does `vitest run` get `passWithNoTests`?
- **Does invariant 100's empty console allow-list apply to all specs or only to the placeholder-route specs?** Finding 13 cannot be closed without this decision.
- **What is the "short cool-down" after a failed revalidation, in milliseconds?**

## What was checked

I read both spec files in full plus `specs/ARCHITECTURE.md` (sections 2, 4, 5 and the three 2026-08-13 decision-log entries), `specs/ROADMAP.md` phase 1, `docs/reference.md` and `CLAUDE.md`, and verified every claim TECH makes about the current repository against `package.json`, `tsconfig.app.json`, `eslint.config.js`, `vite.config.ts`, `index.html`, `.gitignore` and the `src/**` tree — all of TECH's "what the repository is today" statements check out (no `strict`, no `base`, blanket `*.log`, `App.tsx`/`assets` present; the one omission is that `src/vite-env.d.ts`, which TECH's layout and `boundaries/ignore` both reference, does not currently exist). Feasibility attacks targeted the seams: React Router `lazy()` error propagation and hook context above `RouterProvider`, Rollup chunking of dynamically imported JSON, i18next's `missingKeyHandler` vs `parseMissingKeyHandler` semantics, jsdom's inability to apply Tailwind/`@media` for the dual-theme axe run, size-limit's glob-fails-on-empty behavior, and the Vitest project/`setupFiles` split. Claims I could **not** confirm offline and that the spec does not hedge (unlike the `prettier-plugin-tailwindcss` and `size-limit` flags, which it promises to confirm against the installed package): `eslint-plugin-i18next` 6.1.5's option names (`mode: 'jsx-only'`, `ignoreAttribute`), whether `eslint-plugin-boundaries` 7.2.0 resolves `${from.featureName}` when `from` is declared as the bare string `'feature'` rather than a capture matcher, and the existence/size figures for `web-vitals` 6.1.0 — each should be verified against the installed package in M1/M2 before the config is written.
