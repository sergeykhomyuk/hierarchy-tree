### A. Orphans and dangling references from the cache withdrawal

Largely clean. `platform/cache` is gone from the layout; the construction order in §5.1 lists configuration, observability, http, i18next only; there is no cache entry in the coverage config, the size-limit globs, the milestone deliverables, the risks list, or any lint rule path; §3.3 and the testing-map section "Caching (36-44) - withdrawn" both hold the numbers open; PRODUCT's count claim ("135 invariants: 1 through 136 with 36-44 withdrawn, plus the eight suffixed") is arithmetically correct. Two defects: the retired-number convention is broken once, at TECH line 1025 (finding 13); and the rehomed storage rule under 128 is narrower than what it inherited - the service-worker cache clause and the `window.`/`globalThis.` member form are uncovered, and the withdrawn set's e2e storage-emptiness assertion vanished (finding 5).

### B. The Cloudflare move

The split policy is coherent in design - the header policy carries only `frame-ancestors`, the meta policy carries the rest, and two independently-enforced CSPs with disjoint directives cannot conflict - but the "only directive" half is asserted in prose and in invariant 99a and checked by nothing, and the `_headers` check is a containment check where its `_redirects` sibling is an exact-content check, so both a mis-indented (hence Cloudflare-ignored) file and a later-widened file pass (finding 6). The `expected-build-output.json` rule is *not* stated consistently: the key list covers four of the six-plus assertion families §7.1 enumerates, and an M1 implementer cannot decide the base-path, secrets and size-limit-entries obligations (finding 2); "an absent key asserts nothing and passes" does create a silent-no-op hole with no completeness check, and for `kitRouteAbsent` there is no backstop (finding 3). The `/` base path is coherent with invariant 13 - `environment.ts` copies `BASE_URL` into the raw record, `configuration.basePath` is the only downstream reader, and both `createBrowserRouter({basename})` and `window.location.assign(configuration.basePath)` consume it; I found no surviving sub-path assumption in PRODUCT, TECH, ARCHITECTURE or ROADMAP. Invariant 121 is consistent with direct-upload behavior (no automatic previews) *given* one unstated precondition - the project's production branch must be `main`, or `--branch=main` yields exactly the preview 121 forbids (finding 8). The post-merge proof of 123/124 is stated honestly in M6 but incompletely: the prerequisite is unverified before merge and there is no stated remedy if the deployed run fails after merge (finding 10). On security: the `frame-ancestors`-via-`_headers` arrangement is sound in principle, the token handling is specified safely (secrets only, Pages-edit scope, no value in the repo, `--bundle-only` scan over `dist`), but the bundle secrets scan has no file to run in (finding 4), the `_headers` check can pass on a file that ships no protection (finding 6), and the deploy job runs a floating-tag third-party action with unrestricted default token permissions (finding 12).

### C. File conventions

The conventions are applied consistently to the paths in the layout, and the two documented exceptions are genuine, but they do not cover everything the document names - `main.tsx`, `vite-env.d.ts`, `live-smoke.test.ts` and `analyticsEvents.ts` are a de facto third exception (finding 14). One named filename set contradicts a load-bearing consequence of the convention: PascalCase route modules cannot produce the kebab-case chunk names §5.3 and §7.3 depend on (finding 1). The "`index.ts` in every multi-file folder" clause is contradicted by the layout in three folders and, in one of them, would defeat the sink-import restriction (finding 11). No lint rule enforces any naming convention - there is no `unicorn/filename-case`, `check-file` or equivalent in §2, and the testing map has no row for conventions - so they are prose-only. That is acceptable for style, and only a defect where a check's correctness depends on a filename, which is finding 1.

### D. Cross-amendment interactions

Three real collisions: conventions (#3) x build output (#2) at the chunk names (finding 1); conventions (#3) x invariant 45's sink ban at the `index.ts` rule (finding 11); the withdrawn-cache storage rule (#1) x the deploy mechanism - here the spec is *correct*, it explicitly rejects the `sessionStorage` redirect trick in favour of `_redirects` (line 1060), and `_redirects`/`_headers` add nothing to the entry budget, so the size budget is unaffected by the cache's removal beyond a smaller `platform`. The `vitest.build-output.config.ts` added by #3 is indeed the config that runs the deploy assertions from #2, and that seam is where findings 2, 3 and 4 sit. The M5 dependency edge is otherwise sound: `_redirects`/`_headers`, the route/catalogue size entries and all four table keys land in the same milestone as the router that makes them meaningful. The M1 boundary, by contrast, is again over-claimed (finding 9).

### E. Testability of the new and rewritten invariants

99a - build-output half is under-specified and the discriminating half is post-merge (finding 6). 120 - the artifact-identity claim is violated by the e2e rebuild while the named check passes (finding 7). 121 - the `if` condition is checked; the preview-vs-production half depends on unchecked project config (finding 8). 122 - well covered (static scan for the stale prefix plus a `page.on('request')` e2e half). 123/124 - covered, but only after merge; 124's build-output half is the strongest of the file checks. 125/126 - honestly listed as review-dependent. 99/100/103 - checks are named and discriminating. 112 - `npm run size` discriminates, but its guard test (`size-limit-entries.test.ts`) has no declared activation and two different correct contents (finding 2), and its route globs currently match nothing (finding 1). 128 - the lint rule passes against several plausibly-wrong implementations (finding 5). The file conventions have no check at all.
