# Product spec: phase-1-setup - a deployable, instrumented skeleton with no features in it

## Summary

Phase 1 builds the parts of the app that are expensive to retrofit and cheap to get wrong: the four layers with lint-enforced boundaries, the platform adapters (configuration, HTTP, observability, i18n), a domain-free UI kit in light and dark, an app shell that renders two placeholder routes through the real router and provider stack, and the full quality pipeline running in CI with deployment to Cloudflare Pages. The desired outcome is that phases 2 and 3 only ever add feature code: every non-feature concern already exists, is instrumented, and is guarded by a check that fails loudly and specifically when a rule is broken.

## User stories

**As the developer building phase 2 (login) or phase 3 (hierarchy tree)**, I add a feature by creating a slice under `features/`, exporting one public entry, registering a lazily imported route, and adding a translation namespace. I never write a `fetch` call, a retry, a logger, a skeleton, an error state, an empty state or a token value, because each already exists and is the only sanctioned way to do that thing. When I do something the architecture forbids - reach into another feature, import past a feature's public entry, hardcode a user-visible string, read `import.meta.env` directly - I find out from `npm run lint` in seconds, with a message that names the rule and the offending edge, rather than from a reviewer or from production.

**As the reviewer opening the phase 1 pull request**, I start with a URL, not an install. I can see both placeholder routes on the deployed site, confirm that a forced route error renders a recovery UI rather than a blank page, and read a single CI run whose checks tell me, individually, that types are sound, boundaries hold, formatting is settled, coverage clears its threshold, the bundle is inside budget, and the browser suite passed with an uploaded report. I can also see the evidence that the boundary rule really fires: a deliberate cross-feature import and a deliberate deep import, each producing a named lint error, then reverted.

**As CI**, I am the enforcement mechanism, not a smoke alarm. Every rule this spec states is a check I run: a rule with no check behind it is a defect in this phase. When I fail, I say which check, which file, and which limit or rule, so the fix is obvious without re-running anything locally. I never gate on a live third-party database; the live smoke suite is run on demand and cannot block a merge.

**As the person visiting the deployed site** (the only end-user-visible surface in this phase), I load the URL and see a real page: styled, titled, readable in light and dark, in my language, keyboard navigable, and honest that the feature is not built yet. A wrong URL gets a not-found page with a way back, not a blank screen. If something breaks, I get an error message with a way to recover and an identifier the developer can trace.

## Behavior (numbered invariants)

Every invariant is observable: a test, a lint rule, a CI job or a reviewer with the deployed URL can decide it. "Fails lint" means `npm run lint` exits non-zero with an error (not a warning) that names the rule.

### Layer boundaries and their enforcement

1. Exactly four layers exist under `src`: `app`, `features`, `shared`, `platform`. Every source module belongs to exactly one of them; a module that matches no layer fails lint with a message saying it is unclassified.
2. `app` may import from `features`, `shared` and `platform`. (ARCHITECTURE.md section 2 draws only `app -> features` because the diagram is emphasising the forbidden edge; the provider stack and the root error boundary make `app -> platform` and `app -> shared` necessary, and both remain downward edges.)
3. `features/*` may import from `shared` and `platform`, and from their own internals.
4. `shared` may import from `platform` only.
5. `platform` imports from no other layer. An import from `platform` into `shared`, `features` or `app` fails lint.
6. A feature never imports another feature. `features/auth` importing anything under `features/hierarchy`, or the reverse, fails lint with an error naming both feature elements and the forbidden edge.
7. A module outside a feature may import that feature only through its single public entry. Any deeper path into a feature from outside fails lint with a message naming the restricted pattern.
8. `shared` and `platform` are domain-free: no exported name, type, prop, constant or catalogue key in either layer references a domain concept (user, manager, hierarchy, tree, session, login, credential, and the reporting-line sense of "report" - `directReports`, `reportCount`). The mechanical check matches whole identifier segments, not substrings, against a stated allow-list, because a substring match would fail against `encodeURIComponent`, `URLSearchParams` and a `missing-key-reporter` module. A domain type appearing in a `shared` or `platform` signature is a review failure and a defect against this invariant; that half is review-carried in this phase, because no domain type exists yet to detect.
9. Two feature slices exist - `features/auth` and `features/hierarchy` - each with a public entry and no product behavior behind it. They exist so that phases 2 and 3 add code inside an established slice, and so that invariant 6 is demonstrable.
10. The demonstrable negative for cross-feature imports: a deliberate import of `features/hierarchy` from `features/auth` produces a lint error identifying the boundaries rule and the two elements. The error output is captured as evidence and the import is reverted in the same change.
11. The demonstrable negative for deep imports: a deliberate import of a path inside `features/hierarchy` from `app` produces a lint error identifying the restricted-import rule. The output is captured as evidence and the import is reverted in the same change.
12. Boundary rules are configured as errors, so they fail the pipeline. Downgrading one to a warning, or adding a blanket ignore for a layer, is a change that must be argued in the decision log rather than made silently.

### Configuration

13. Exactly one module reads `import.meta.env`. A read of `import.meta.env` anywhere else in `src` fails lint with a message pointing at the config module.
14. Configuration is read once at startup and exposed as a typed, frozen, read-only object. Mutating it at runtime is a type error.
15. Configuration is validated against a schema at startup, before the app renders anything. Validation covers, at minimum: the API base URL (a valid absolute URL), the log level (one of the allowed levels), the observability sink selection, and any feature flag.
16. Invalid or missing configuration fails fast and visibly: the app does not render a partially configured UI and does not render a blank page. It renders an error surface naming which key or keys failed validation, and the failure is reported through the observability facade.
17. Configuration values that fail validation are named in the message; their values are never printed, because a value that reaches a log is a value that reaches a sink.
18. Every configuration key has an environment-shaped default, so a checkout with no environment file starts in development and passes the whole pipeline.
19. Configuration is injectable in tests: a test can construct a config object with overridden values without mutating process or import-meta environment state, and without leaking into another test.
20. Nothing in configuration is secret. The bundle is public, so any value that would be a secret is by definition not a configuration value in this app - see invariant 133.

### HTTP client

21. Every network request in the app goes through one HTTP client. A direct call to `fetch`, `globalThis.fetch`, `window.fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `navigator.sendBeacon` or `new Image().src` outside the client's transport module fails lint - those identifiers are the enumerated ban list, not an illustrative sample. A transport constructed indirectly at runtime (a computed member access, a string-built global lookup) is not lint-detectable; that residue is review-carried and named as such.
22. The client resolves request paths against the base URL from configuration. Callers pass a resource path; a caller passing an absolute URL is a type error or is rejected by the client.
23. Every request is given a deadline, and the deadline is **per logical request, not per attempt**: it starts when the caller calls the client and covers the first attempt, the backoff wait and the retry together. A caller passing 8000 ms waits at most 8000 ms for the whole call. When the deadline passes - during either attempt or during the backoff - the in-flight attempt is aborted via `AbortController`, no further attempt starts, and the caller receives a `TimeoutError`.
24. A caller-supplied abort signal composes with the client's deadline: aborting from the caller aborts the underlying request, including during the backoff wait. The abort reason distinguishes the two sources, so a deadline abort and a caller abort never resolve to the same outcome.
25. A caller-initiated abort is not a failure. It is never retried, is never reported as an application error, and is returned as its own `cancelled` outcome, distinct from every failure the client can produce (invariant 33). A caller that cancels a request on unmount cannot render an error state by mistake, because there is no failure value to render. A signal that is already aborted when the client is called yields `cancelled` with no transport call at all.
26. At most one retry is ever attempted for a request, so a failing endpoint costs at most two round trips.
27. Retry applies only to GET. A non-GET request is never retried, regardless of the failure.
28. Retry applies only to network failures, timeouts and 5xx responses. A 4xx response is never retried.
29. The retry delay is exponential backoff with jitter, bounded by a maximum. The delay is computed from injected clock and randomness sources, so a test can assert the exact delay rather than sleeping.
30. Every outbound request carries a W3C `traceparent` header in valid format, with a fresh span id per request and a trace id equal to the correlation id for the interaction (invariant 47).
31. Every request emits one timing record through the observability facade containing method, resource path, outcome, HTTP status when there is one, duration and correlation id. A retried request emits a record per attempt, distinguishable as attempts of the same logical request.
32. The transport is injected. Component and unit tests substitute a fake transport without a mock server, without patching globals, and without network access. Every Vitest project - not only the jsdom one - loads the setup file that makes a real `fetch` throw, so the HTTP suite itself is covered by that guarantee rather than exempt from it.
33. A call has exactly three outcomes: success, failure and cancelled. **Failures** are exactly one of four types: `NetworkError`, `TimeoutError`, `HttpError` (carrying the status code) and `ParseError`. That four-member union is exhaustive and discriminable by a literal tag, so a `switch` over it typechecks without a default branch. The union describes failures only - cancellation (invariant 25) is a sibling outcome, not a fifth member, so adding cancellation does not widen it.
34. No raw platform error escapes the client. Anything the transport throws that does not map to a more specific case becomes a `NetworkError`; callers never see a bare `TypeError`.
35. Error objects carry no request or response body content beyond the status and a safe status description, so a response containing sensitive material cannot travel inside an error into a log.

### Caching - withdrawn (36-44)

Caching is out of scope, for this phase and for the roadmap. The withdrawn design, its nine invariants and the ten review findings it absorbed are preserved in [../CACHE.md](../CACHE.md). Specifying it produced the largest single piece of this document - a six-state entry machine, per-key generations, revalidation cooldowns and their tests - to save one 9KB request against a dataset of 33 users. ARCHITECTURE.md's decision log records the withdrawal; nothing in phases 1 to 3 builds `platform/cache`, and the repository per resource is the seam a cache attaches behind if it is ever worth its complexity.

36. through 44. **Withdrawn.** The numbers are retired rather than reused, so every invariant from 45 onward keeps the identity it carries in the review record, in `loop.json` and in TECH.md's testing map. A future loop that reintroduces caching writes new invariants under its own numbering.

One rule from the withdrawn set survives on its own merit, and it moves to invariant 128 rather than staying here: nothing in this phase writes to `localStorage`, `sessionStorage`, IndexedDB or a service worker cache, and the lint rule banning those globals is installed in phase 1.

### Observability

45. The observability **facade** exposes exactly three interfaces: logger, tracer, analytics - no fourth key. No module outside `platform/observability` imports or constructs a sink. This invariant is about the facade's surface, not about the factory's return value; see invariant 45a.
45a. The factory that builds observability returns two values: the facade of invariant 45, and a read handle on the ring buffer when the buffer sink is selected (otherwise nothing). The handle exists so e2e can read what was recorded (invariant 49) without any module importing a sink. Attaching that handle to a global belongs to exactly one module in `app`, is gated on a configuration flag, and is a lint failure anywhere else. `platform` never writes to `globalThis`.
46. Sinks are selected once, at composition: console in development, a bounded in-memory ring buffer in production builds, no-op in tests unless a test opts in to the buffer.
47. Every interaction has one correlation id. Any error a boundary reports and the analytics event for that interaction carry it, and it equals the trace-id component of the `traceparent` sent on the wire. In this phase nothing fetches during a navigation, so the request-record half of the correlation is proven by unit tests against the fake transport, and e2e proves the boundary report and the analytics event share the interaction's id.
47a. An interaction begins when a router navigation starts, **including the initial page load**, and ends when the router settles. One module owns that lifecycle - the router subscription in `app` - and it is the only producer of interaction ids. A navigation that settles successfully emits exactly one `app.route_viewed` carrying the matched route id. A navigation that ends in an error emits **no** `app.route_viewed` and exactly one `app.error_boundary_shown` carrying the same correlation id, because a route that failed to load was never viewed.
48. The ring buffer is bounded: past its capacity the oldest entries are dropped and memory does not grow with session length.
49. The ring buffer is readable, so e2e asserts on what was recorded. The telemetry contract is tested behavior, not documentation.
50. Analytics events are a typed union with a documented catalogue. Emitting an event name outside the union is a type error, and renaming an event is a compiler-guided refactor.
51. Analytics event payloads are typed per event; a payload with a wrong or missing field is a type error.
52. Web Vitals LCP, INP and CLS are collected through the `web-vitals` package and reported through the same facade, as the metrics they are actually named after. `PerformanceObserver` alone cannot compute INP's percentile-with-windowing rule or CLS's session-window maximum, and reporting a maximum interaction latency under the label `INP` would make the telemetry lie. The dependency is a deliberate exception to invariant 134, recorded in ARCHITECTURE.md's decision log.
53. Where the underlying `PerformanceObserver` or a given entry type is unsupported, collection degrades silently: no throw, no console noise, no broken page.
54. A redaction layer runs inside the facade, before any sink is called, so a careless caller cannot bypass it.
55. Redaction removes values under any key matching `password`, `secret` or `token`, case-insensitively, at any depth, including inside arrays, and including query-string parameters of any URL in the payload. The value is replaced with a fixed placeholder; the key remains so the shape stays readable.
56. Redaction is proven by a test that passes a nested payload containing each key at several depths and asserts no sink received any of the original values.
57. The configured log level is honored: a call below the threshold produces no sink call at all.
58. No sink transmits anything off the device in this phase. There is no vendor SDK and no telemetry endpoint.
59. Observability calls never throw into application code. The guard covers the **whole** call - the level check, the redaction traversal and the sink write - not only the sink write, so a payload carrying a throwing getter, a revoked proxy or a structure deep enough to overflow the traversal cannot break a render or a request. A failure anywhere inside the facade is swallowed.

### Internationalization

60. Every user-visible string comes from an i18next catalogue. A hardcoded user-visible literal in JSX fails lint with the `i18next` rule id.
61. Catalogues are organised as one namespace per feature, plus a common namespace for the shell and the UI kit.
62. A feature's namespace is lazily loaded with its route, so the login chunk does not carry hierarchy strings and vice versa. Lazy namespace loading is exercised end to end in this phase, with placeholder namespaces, rather than left to phase 2 to discover.
63. A missing translation key is a failure, not a silent fallback to the key. The behavior is the same in every environment - development, test and production - so a missing key cannot hide in the build that ships: the key is reported through the observability facade at error level, and what renders is a visibly wrong marker (`⟦namespace:key⟧`) that no reviewer would mistake for copy. Only the sink differs by environment. The unit suite additionally fails if any rendered surface requests a key that does not exist.
64. Dates, numbers, names and lists are formatted through `Intl` (`DateTimeFormat`, `NumberFormat`, `ListFormat`, `Collator`). Building any of these by string concatenation, or hand-rolling pluralization instead of using i18next plural forms, is a defect.
65. English is the only shipped locale. The infrastructure carries no locale-specific branching, so adding a locale is adding a catalogue.
66. The document `lang` attribute reflects the active locale, and `dir` is derived from the locale rather than hardcoded on the element. The derivation is an explicit locale-to-direction map in the i18n module, not a runtime `Intl` API: `Intl.Locale.prototype.getTextInfo` is declared only in TypeScript's `esnext.intl` library and does not typecheck under this repository's `ES2023` + `DOM` libs, and widening the lib to pull in a stage-3 API for a single-locale app is a worse trade than four lines of map.
67. Layout uses logical properties throughout. No physical-direction spacing or alignment (`margin-left`, `padding-right`, `text-align: left`, and their utility equivalents) appears in shipped styles; this is grep- and review-checkable.
68. Switching the document direction to RTL mirrors the placeholder pages correctly with no other code change, so an RTL locale needs a catalogue and a `dir` switch and nothing else.

### The shared UI kit

69. The kit consists of the token layer plus eight components: `Button`, `Field`, `Input`, `Card`, `Avatar`, `Skeleton`, `ErrorState`, `EmptyState`.
70. Design tokens - color, spacing, type scale, radii, motion - are declared once. The light values are the mockup values recorded in `docs/reference.md`.
71. The dark theme is defined over the same token names, so a component never branches on theme. A component referencing a raw color value instead of a token is a defect.
72. Both themes hold WCAG AA: 4.5:1 for body text, 3:1 for large text, icons and UI boundaries. This is asserted by an automated contrast check over the token pairs the components actually use, not eyeballed against the mockup.
73. The dark theme activates from `prefers-color-scheme`. There is no theme switcher in this phase.
74. Every interactive element has a visible focus indicator that meets 3:1 against its adjacent colors in both themes. No component removes the focus outline without replacing it.
75. Under `prefers-reduced-motion: reduce`, all transitions and animations are disabled, including the `Skeleton` shimmer.
76. `Skeleton` reserves the dimensions of the content it stands in for, so swapping skeleton for content produces no layout shift. Dimensions arrive as a closed set of kit-local size tokens shared with the content, and the component emits **no `style` attribute** - the production CSP sets `style-src 'self'` with no `'unsafe-inline'`, so an inline width or height would be blocked by the browser and would raise the CSP violation invariant 100 forbids. The proof is a browser measurement: the skeleton's box and its replacement content's box are equal.
77. `Avatar` renders an image with explicit width and height, `loading="lazy"`, and `referrerpolicy="no-referrer"`.
78. `Avatar` falls back to initials when no image source is given or when the image fails to load, and the fallback is derived from a display-name string passed as a prop - the component knows nothing about a user record.
79. `Avatar` exposes an accessible name when it conveys information and is hidden from assistive technology when it is decorative; which of the two applies is a prop, not a guess.
80. `Button` supports a primary and a secondary variant, a disabled state and a busy state. Busy sets `aria-busy` and `aria-disabled`, keeps the accessible name and keeps the element focusable, and suppresses the activation itself - it calls `preventDefault()` before anything else, so a busy `type="submit"` cannot submit its form by pointer or by keyboard, and `onClick` is not invoked. Ignoring the handler alone is not enough.
81. `Field` associates its label with its control programmatically, links its error and hint text via `aria-describedby`, sets `aria-invalid` when in error, and communicates required state. A placeholder is never used as a label.
82. `ErrorState` renders a message, an optional correlation id, and a recovery action rendered as a real focusable button with an accessible name.
83. `EmptyState` renders a title, an explanatory message and an optional action.
84. Every kit component is domain-free: props are primitives, `ReactNode` or kit-local types. No domain type appears in any signature.
85. No kit component contains a user-visible literal. All text arrives as props from a catalogue, so the kit is reusable across locales and features.
86. Every kit component renders correctly from a 320px viewport upward without horizontal overflow. All eight are proven in a real browser, not inferred from the two placeholder pages, because five of them appear on no product surface in this phase.
86a. A development-only kit route exists at `/__kit`, mounted only when a build-time flag is on, rendering every documented state of all eight components from one shared state inventory. Playwright exercises that route at a 320px viewport with axe, in real light and real dark (the browser's `colorScheme`, not a stubbed media query), and measures the skeleton-to-content swap of invariant 76. This is a narrow verification surface, not a design-system site: it has no navigation, no documentation prose and no link from the app.
86b. The production build contains no kit route. The flag is a build-time constant, so the route module and its state inventory are dropped by the bundler, and a build-output check asserts that no `dist` file contains the kit route path, the kit chunk or any state-inventory marker. A kit route that survives into `dist` fails the pipeline.
87. Every kit component is covered by unit tests that render each of its documented states and assert zero axe violations. Those unit assertions run in light only: jsdom applies no stylesheet, so a dark run there would assert the same DOM twice and prove nothing. Dark-theme axe coverage is the browser run on the kit route (invariant 86a). "Documented states" is a single inventory module consumed by both the unit tests and the kit route, and a check fails when a component exported from the kit has no state in it.

### The app shell

88. Routing uses React Router in library mode with `createBrowserRouter`, configured for the deployment base path, so the build output stays static files.
89. Route modules are lazily imported, and the production build emits a separate chunk per route. This is verified against build output, not assumed.
90. The provider stack is composed in exactly one place, with a documented order, and covers configuration, i18n, observability and the root error boundary. Rendering a route in a test goes through the real stack.
91. A route that throws during render, or a loader that rejects, renders the root error boundary. The user sees the `ErrorState` with a recovery action; the user never sees a blank page, a raw stack trace or an unstyled browser error.
92. The boundary reports the error exactly once through the observability facade, with a correlation id, and displays that same correlation id to the user, so a screenshot ties to a log entry.
93. Recovery from the error boundary works and is reachable by keyboard. The recovery is supplied by whichever boundary is rendering, never derived by the error surface itself: the route boundary re-attempts the failed route through the router, and the root boundary - which renders above the router, where router hooks are unavailable - reloads the document at the application base path. The shared error surface takes the recovery as a prop and calls no router hook, so the root boundary cannot throw a second time while rendering the recovery UI.
94. The router serves a placeholder route at `/login` and a placeholder route at `/`.
95. Both placeholder pages render through the UI kit with catalogue strings, set a document title from the catalogue, expose exactly one `h1`, sit inside a `main` landmark, are fully keyboard reachable, and pass axe with zero violations.
96. Both placeholder pages read as placeholders. Neither promises or simulates a feature that does not exist.
96a. The `/login` placeholder is generic. It uses kit components, catalogue strings, the login canvas token and the type scale, but carries none of mockup screen `1a`'s chrome: no nav rail, no centered login card, no brand mark. Screen `1a` is built once, in phase 2, where it can be compared against the mockup in a single pass. Building the card shell here would be feature-shaped code with no behavior behind it, which invariant 136 forbids.
97. There is no route guard, no redirect between `/` and `/login`, no session read and no data fetch in this phase. Both routes are reachable directly.
98. Any unmatched path renders a not-found route with an explanation and a link back to the home route. It is not the error boundary and not a blank page.
99. The delivered HTML carries a Content-Security-Policy meta tag that at minimum sets `default-src 'self'`, `object-src 'none'`, `base-uri 'self'`, and a `connect-src` that includes the configured API base URL. It does NOT set `frame-ancestors`: that directive is ignored inside a meta tag and browsers warn about it, so including it would buy nothing and force a console allow-list entry that invariant 100 depends on staying empty. Clickjacking protection is a response header instead - see invariant 99a. `img-src` allows only `'self'` and `data:` - no remote host. Phase 3 reads the live `users` payload, learns the actual avatar hosts, and widens `img-src` as a reviewed change with a decision-log entry. Shipping a permissive `img-src` now, before there is evidence of which hosts are needed, is explicitly rejected.
99a. Framing protection ships as a response header, because the meta tag cannot carry it. The build output contains a `_headers` file declaring `Content-Security-Policy: frame-ancestors 'none'` for every path, which Cloudflare Pages serves as a real header. It is deliberately the only directive in the header: the meta tag stays the single place the rest of the policy is read, and two half-policies that can disagree is the failure mode this split avoids. That exclusivity is **asserted, not just described**: the build-output check compares `dist/_headers` against its exact expected content byte for byte - the `/*` path line and the one indented header line and nothing else - so an added directive fails the check exactly as a missing one does. An exact-content assertion is what the sibling `_redirects` check already uses (invariant 124), and it is required here for a second reason: Cloudflare's `_headers` format silently ignores a header line that is not indented under its path block, so a containment check would pass a file that ships no framing protection at all. The deployed smoke run then asserts the header actually arrives on the live response, which is the only check that can distinguish a correct file from a correctly-formatted file the host did not apply. The residual gap the previous hosting choice left - no framing protection at all - is closed rather than recorded.
100. No route produces a CSP violation, and the console carries no error or warning, in both the development server and the production build. React's root is created with `onCaughtError` and `onUncaughtError` handlers that route boundary-caught errors to the observability facade instead of the default `console.error`, so an error the app handles never reaches the console. The allow-list is empty for every spec but one. The forced-error spec aborts a lazy route chunk, and an aborted subresource makes the BROWSER log a network error that no application code can intercept; that spec therefore asserts an exact expected set - the single aborted-request entry, matched by URL - and fails on any other entry. An exact expected set is not an open-ended allow-list: it fails on a new entry exactly as an empty assertion would, which is the property this invariant depends on. Widening it, or adding an entry to any other spec, requires the same argument as downgrading a lint rule.
101. `index.html` carries `lang`, a viewport meta, a title, and a favicon that belongs to this app.

### The quality pipeline

102. Each **gating check** is one npm script, and CI runs exactly those scripts. There is no gate that exists only in the workflow file, so a check that passes locally passes in CI for the same reason. Infrastructure setup steps are exempt and named explicitly - `npm ci` and `npx playwright install` are the whole allow-list; a run line that is neither an npm script nor an allow-listed setup command fails the workflow-parse test. The rule's scope is the **`verify` job**, which is where every gate lives. The `deploy` job is not a gate - it runs only after `verify` has passed, only on `main`, and it cannot make a failing change green - so its steps are outside this rule. That is not a loophole for smuggling a check into the workflow: the deploy job's one assertion (invariant 123's deployment-URL comparison) is about the deployment itself, which by definition has no local equivalent to run, and it is the only such step this phase permits. A new `run:` line in the `deploy` job that checks the *code* rather than the deployment is a violation of this invariant's intent and is caught in review.
103. One GitHub Actions workflow runs on pull requests and on pushes to `main`, in this order: typecheck, lint, format check, unit tests with coverage, build, build-output assertions, size budgets, e2e. The build-output step exists because several checks can only inspect `dist` - the bundle secrets scan, the base-path scan, the route and catalogue chunk assertions, the kit-route absence check and the `_redirects`/`_headers` files - and a check that runs before the build exists is not a check.
104. Typecheck failing means the code is not type-sound. `strict` is enabled in `tsconfig.app.json` (it is currently missing), and type-aware ESLint rules are configured so lint sees types.
105. `any` and non-null assertions fail lint. A suppression comment for a type or boundary rule requires an adjacent justification, and none appears in shipped `src` for those rules.
106. Lint failing means either a correctness rule or an architecture rule was broken: boundaries, restricted imports, `jsx-a11y`, `react-hooks`, `i18next` literals, testing-library and Playwright hygiene. Lint output names the rule so the category is unambiguous.
107. Format check failing means Prettier would rewrite a file, including Tailwind class order. Formatting is never argued in review.
108. Unit tests run under Vitest with jsdom and Testing Library. Component tests assert behavior and keyboard interaction and inject a fake transport; none of them touches the network.
109. Coverage thresholds are enforced at 85% for lines, branches and functions globally. Falling below fails CI.
110. A 100% threshold for `src/features/*/domain` is configured now and takes effect when such a directory exists in phase 3. It must not fail the phase 1 build, and phase 3 must not be able to ship without it.
111. Build failing means the production bundle cannot be produced. The build runs the typecheck as part of `npm run build`.
112. Size budgets are checked by `size-limit` against the production build, and every emitted chunk class has an entry: the initial payload (entry plus vendor) at most 150 kB gzipped, the stylesheet at most 15 kB gzipped, each per-route chunk at most 30 kB gzipped, and each lazily loaded catalogue chunk at most 5 kB gzipped. Exceeding a budget fails CI with actual and limit printed. The figure was originally set at 100 kB against an estimate of 85-90 kB for the **fixed runtime dependency set alone** (react-dom, react-router, zod, i18next, react-i18next, web-vitals). Wiring the real router in M5 measured the entry at 112.77 kB and busted that number; an isolated tree-shaken probe of `createBrowserRouter`/`RouterProvider` alone put react-router's own weight at roughly 31 kB gzipped, showing the original estimate had undercounted react-router specifically rather than the build regressing. Per this invariant's own rule, the number was revisited with the user rather than silently raised, and the user set the corrected budget at 150 kB. That is measured from the first milestone rather than the last, and if a future measurement contradicts the estimate again the number is again revisited with the user, never silently raised.
113. E2E runs Playwright against the production build with `route()` mocks. In this phase it covers: both placeholder routes render, the not-found route renders, a forced route error renders the boundary with a correlation id and a working recovery action, the buffer sink recorded the expected events, the console is free of errors, and axe passes on each rendered route.
114. The Playwright HTML report is uploaded as a CI artifact on both success and failure, so a failing run is diagnosable from the run page without reproducing locally.
115. Unit and e2e runs are deterministic. Time and randomness are injected, no test depends on wall-clock timing or on a real host, and a test attempting real network access fails.
116. A live smoke job against the real database exists as a manually triggered job only. It never runs on a pull request or on `main`, and its failure cannot block a merge. Its test file lives **outside `src`** and outside every default Vitest project, so no gating command can collect it even by accident; it runs only under its own config.
116a. The phase 1 live smoke is a reachability and shape probe: it requests the configured base URL through the real HTTP client, asserts the response parses as JSON, asserts that top-level `users` and `secrets` keys are present, and prints the field names observed on one `users` record. The printed field names are the deliverable - `docs/reference.md` records the user record's field names as unconfirmed and requires reading them from the live database before any schema is written, which phase 3 needs.
116b. The live smoke asserts nothing about field names it printed. Discovering that the live shape changed is a phase 3 concern; phase 1 only proves the endpoint is reachable and the two expected top-level keys exist.
117. CI runs on the Node version pinned in the repository, matching local development, so a version drift is a visible change rather than a mysterious failure.
118. Every check is runnable locally with one documented command, and the commands are listed where a new contributor will find them.
119. The phase is not claimed done on an unrun suite. Every claim in the phase's proof points to a run that happened.

### Deployment

120. A push to `main` deploys the built site to Cloudflare Pages from the same GitHub Actions workflow, and only after every gating check has passed. The deploy step is `wrangler pages deploy` against the already-built `dist`, so the artifact that was verified is the artifact that ships - nothing is rebuilt for the deploy.
121. Pull request builds never deploy. No preview deployment is created either: a pull request produces a CI run, not a URL.
122. The site is served from the root of its own hostname, so the Vite base path is `/` and every asset and route URL is root-relative. No URL in the built output carries a project sub-path, and a stale `/hierarchy-tree/` prefix anywhere in `dist` fails the build-output check.
123. The deployed site renders the placeholder home route at its root URL. The URL is the Cloudflare Pages project's production hostname, recorded **once, in one machine-readable place** - `deployment.json` at the repository root, holding the project name and the production hostname - so that the workflow, the deployed Playwright project and the documentation all read the same value rather than each carrying a copy that can drift. A prose document cannot be that place: a workflow step cannot read a sentence out of `VERIFICATION.md`, so recording it only there guarantees a second hardcoded copy in `ci.yml`. `VERIFICATION.md` and `.env.example` cite the value, and a unit test asserts the value they cite matches `deployment.json`, which is what keeps the documentation honest without making it the source. The deploy step records both the deployment's own permanent URL and the recorded production hostname to the job summary, but does not compare them: Wrangler's `deployment-url` output is always the deployment's own `<hash>.<project>.pages.dev` permalink, never the production alias, regardless of whether Cloudflare has actually flagged that deployment production (see ARCHITECTURE.md's decision log, 2026-08-14). A mis-configured project (invariant 126) is instead caught by invariant 126a's post-merge `e2e:deployed` run, which fetches the real production hostname directly and is the one check in this pipeline that can distinguish a correctly routed deployment from a stale one.
124. `<deployed-base>/login` renders the placeholder login route on a direct load and after a browser refresh, not a 404. Deep links work because the build output carries a `_redirects` rule serving `index.html` with a 200 status for any unmatched path. This is the phase's third exit criterion and is proven against the deployed URL in this loop.
125. Concurrent pushes to `main` do not race: a newer deploy supersedes an in-flight one rather than interleaving with it.
126. The deployment depends on manual, one-time setup performed by the repository owner, and the list is exhaustive because every item on it is invisible to CI: a Cloudflare Pages project created with direct-upload (not Git integration, which would deploy without waiting for the gates); **the project's production branch set to `main`**; and `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` stored as repository secrets. The token carries the Pages edit permission and nothing else. The production-branch item is load-bearing rather than administrative: Cloudflare decides production-versus-preview by comparing the upload's `--branch` against the project's configured production branch, so if they disagree, `wrangler pages deploy --branch=main` succeeds, reports a preview URL, and leaves the production hostname stale while the job stays green. No mechanical check in the deploy job itself catches this - Wrangler's reported URL cannot discriminate the two cases (see invariant 123, corrected 2026-08-14). Invariant 126a's post-merge `e2e:deployed` run is what turns that silent case into a failure, one step later than originally designed. This whole list is named as a prerequisite in the change, so a failed first deploy is diagnosable in seconds, and no secret value appears in the repository (invariant 133).

126a. Invariants 123 and 124 cannot be proven before merge, and the phase does not pretend otherwise. Invariant 121 forbids preview deployments, so no pull-request run produces a URL to test; this is a deliberate trade - preview deploys would make the exit criterion provable on the pull request, and they are rejected because they put a deploy surface and a live token on every pull request, including forks. The consequence is an explicit obligation rather than a gap: after the merge to `main`, the deploy job runs and `npm run e2e:deployed` is run against the recorded production hostname, its output is captured as evidence, and **the phase is not complete until it passes** (invariant 119). If it fails, the phase is not silently done - the failure is the loop's, a fix lands on a follow-up branch through the same gates, and the deployed run is repeated. No milestone boundary and no pull-request run may claim invariants 123 or 124 as verified.

### What must not be true at the end of this phase

127. No login behavior exists: no credential-to-secret derivation, no lookup table, no `/secrets` request, no password handling of any kind.
128. No session exists: there is no logged-in user concept, no route guard and no logout. Nothing in the app writes to `localStorage`, `sessionStorage`, IndexedDB or a service worker cache, and a use of any of those globals in `src` fails lint - the rule that carries the storage half of this invariant, inherited from the withdrawn caching set. The banned set is enumerated, not illustrative: `localStorage`, `sessionStorage`, `indexedDB`, `caches` (the `CacheStorage` global, which is the service-worker cache this invariant names) and `navigator.serviceWorker`. Each is banned in **both** the bare-identifier and the member forms - `window.localStorage`, `globalThis.sessionStorage` and their siblings - because a bare-identifier rule alone matches neither, which is the same pairing the network ban of invariant 21 already uses. A storage global reached by computed member access is not lint-detectable; that residue is review-carried and named as such. Phase 2 removes the `sessionStorage` entry from that rule with a decision-log line, because the session record is what first needs it.
129. No hierarchy behavior exists: no `buildForest`, no `flattenVisible`, no tree widget, no users request, no user schema, no avatar data.
130. No repository module for a real resource exists. The HTTP client is exercised by tests against a fake transport and fixtures, not against a domain resource.
131. No Vite template cruft remains in `src` or `public`: the template's `App` component, its stylesheet and its unused logo assets are gone. (The README rewrite belongs to phase 3 per ROADMAP.md and is out of scope here.)
132. No placeholder page contains lorem ipsum, a fake form, or a control that does nothing when activated.
133. No secret, token, API key, credential or private endpoint appears in the repository, in the bundle, or in any environment file. Everything shipped is public by construction, because a static client bundle is public.
134. No runtime dependency is added beyond what these invariants require, and each added dependency is justified against the size budget. The allow-list is exactly `react`, `react-dom`, `react-router`, `zod`, `i18next`, `react-i18next` and `web-vitals`; a check fails when `dependencies` stops matching it, so a new one is a deliberate edit rather than a drift. Specifically excluded: no data-fetching library, no component library, no telemetry vendor SDK, no polyfill for something the pinned Node and target browsers already have. `web-vitals` is on the list by the explicit decision recorded at invariant 52, not by default.
135. No check in the pipeline is disabled, skipped or set to continue-on-error to make the phase green.
136. No feature-shaped code is parked in `app`, `shared` or `platform` in anticipation of phases 2 and 3. An abstraction with no caller in this phase is not built.

## Goals / Non-goals

**Goals**

- The four layers exist and their import rules are enforced by lint, with both forbidden edges demonstrated failing and then reverted.
- The platform layer adapts the outside world: typed validated configuration, one HTTP client with timeout, bounded retry, trace propagation and a typed error union, an observability facade with swappable sinks and a redaction layer, and i18n with lazy per-feature namespaces.
- A domain-free UI kit carries the mockups' visual language in light and dark, at WCAG AA, with visible focus, reduced-motion support and logical properties, and all eight components are proven in a real browser through a development-only kit route that never reaches production.
- The router, provider stack and root error boundary compose an app that renders `/login`, `/` and a not-found route.
- The whole quality pipeline runs in CI in a defined order, with coverage thresholds, size budgets and an e2e report artifact.
- `main` deploys itself to Cloudflare Pages after the gates pass, and the deployed URL renders the placeholder login route on a direct load.

**Non-goals**

Belonging to phase 2:

- Login form, credential-to-secret derivation, the `/secrets` lookup, authentication error states, session persistence, the route guard and the `from` redirect.

Belonging to phase 3:

- The tree domain, tolerant per-row validation, the users request, the ARIA tree widget and its keyboard contract, URL-persisted expansion state, the header with the signed-in user and logout, the summary line and per-row report counts, and the README rewrite.

Deliberately not built at all (ARCHITECTURE.md section 7):

- Response caching - in-flight dedupe, TTL, stale-while-revalidate. Withdrawn from the roadmap on 2026-08-13, not deferred to a later phase: no phase builds `platform/cache`, and the repository per resource is the seam a cache attaches behind if one is ever wanted. Invariants 36-44 are retired with it.
- Virtualized rendering. Unnecessary at 33 rows; `flattenVisible` will emit the row model a windowing layer consumes.
- Real authentication. Impossible against this API from a static client; `features/auth` isolates the lookup so a BFF-issued cookie replaces one module.
- Offline support and service workers. A 9KB public payload does not justify a cache lifecycle; the repository layer is where a persistent cache would attach.
- Search, filtering and org editing. Outside GOAL.md.
- A second locale, SSR and a component library. The infrastructure supports each; none is needed.
- Vendor telemetry. The facade defines the contract; a real sink is a sink swap.

Also out of scope for this phase specifically:

- A theme switcher, a design-system documentation site, or a component gallery that ships. The development-only kit route of invariant 86a is in scope and is not a gallery: it is a verification surface that renders the state inventory, carries no documentation and no navigation, and is absent from the production build by invariant 86b. A gallery page reachable by a user of the deployed site remains out of scope.
- Performance tuning beyond meeting the stated size budgets.
- Any CI job that gates on the live third-party database.

## Open questions

All four questions raised during drafting were settled with the user on 2026-08-13, before TECH.md was written. None remain open.

- **Placeholder fidelity** - resolved: the `/login` placeholder stays generic; mockup screen `1a` lands whole in phase 2. Encoded as invariant 96a.
- **Dark theme values** - resolved: derive the dark palette over the same token names and let the automated WCAG AA contrast assertion be the gate. No separate human review round before phase 2; invariants 71 and 72 already carry the constraints, and the design flag is off for this loop because the mockups are the existing visual reference.
- **CSP image sources** - resolved: ship the tight policy now (`img-src 'self' data:`) and widen it in phase 3 against evidence from the live payload. Encoded as invariant 99.
- **Phase 1 live smoke content** - resolved: it ships as a reachability and shape probe that also prints the observed `users` field names, which phase 3 needs. Encoded as invariants 116a and 116b.

The G1 validation round (two independent reviewers, 42 findings, recorded under `evidence/reviews/`) raised eight further questions. All were settled on 2026-08-13 and encoded here rather than left open:

- **Is the request deadline per attempt or per logical request?** Per logical request - invariant 23.
- **What outcome does a caller-initiated abort produce?** Its own `cancelled` outcome, leaving the four-member failure union untouched - invariants 25 and 33.
- **What does a read see during a revalidation, and what does a failed revalidation do to freshness?** Moot: caching is withdrawn (invariants 36-44). The cost of answering this question, and the two either side of it, is what the withdrawal decision was made on.
- **What happens to an in-flight load when `invalidate` or `clear` runs?** Moot, as above.
- **What does a missing key render in production?** The same visible marker as everywhere else, reported through the facade - invariant 63.
- **How are the five kit components with no product surface proven?** The development-only kit route - invariants 86a and 86b.
- **Does the empty console allow-list cover the forced-error spec?** Yes; React's `onCaughtError` routes the error to observability instead of the console - invariant 100.
- **Does a failed navigation emit `app.route_viewed`?** No - invariant 47a.

One question the reviewers raised is deliberately **not** settled here, because phase 1 cannot answer it: whether the `traceparent` header triggers a CORS preflight against the live database. The live smoke runs under Node, where CORS is not enforced, so the probe cannot discover it. It is recorded as a phase 2 risk in TECH.md rather than as a phase 1 invariant.
